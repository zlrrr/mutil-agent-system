# IncidentOps Arena — 需求规格

## 1. 阅读指引

需求陈述的是**什么**必须可被观察为真，而绝非**怎么做**。每条需求都可测试：它给出的是一个
测试能够断言的条件。`必须（MUST）`是规范性的，其余部分是上下文。

需求标识符按领域分组，但领域调整时不会重新编号，因此标识符是永久句柄。

## 2. 术语表

| 术语 | 定义 |
|---|---|
| Case（调查案例） | 针对一条告警的一次完整调查，从接入直到报告关闭 |
| Evidence（证据） | 来自单一数据源的不可变、有标识的观测，限定在一个时间窗内，并携带指向产生它的原始查询的引用 |
| Evidence kind（证据类别） | 取值之一：metric、log、change、topology、knowledge、verification |
| Hypothesis（假设） | 候选根因，带有机理叙述、支持证据与反证，以及可拆解的分数 |
| Critique（质疑） | 针对某个假设的结构化反对意见，携带裁决，并可选地携带对特定补充证据的索取 |
| Contribution（贡献） | Agent 唯一被允许返回的东西：请求新增证据、提出假设、发起质疑、索取证据、提议动作、或记录验证 |
| Action（动作） | 对目标系统的一次拟议变更，携带风险等级、前置条件、回滚方案与验证步骤 |
| Round（轮次） | 一次采集、假设形成与质疑的完整过程。轮次有上限 |
| Reasoner（推理器） | 可插拔组件，在给定证据的前提下决定 Agent **如何**得出结论 |

## 3. 领域契约

<!-- sdd:item id=REQ-0001 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0001 — Agent 之间只通过带类型的贡献通信

**需求。** Agent 必须返回一组带类型的贡献，且不得直接修改 case 状态。自由形式的自然语言
不得作为 Agent 之间决策的载体；散文只能出现在带类型记录的摘要字段内。

**理由。** 正是这一点让 Agent 可以被独立测试、安全并行，并让编排器成为唯一写入方，从而
成为事件日志的唯一来源。

**验收。**
- 给定任意 Agent 与任意 case 快照，当该 Agent 运行时，则 case 保持不变，返回的贡献是其
  唯一效果。

**验证方式。** TC-0001

<!-- sdd:item id=REQ-0002 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0002 — 证据不可变、有标识、可回溯到其查询

**需求。** 每条证据必须携带稳定标识符、产出它的 Agent、来源适配器、类别、覆盖的时间窗、
可读摘要、指向产生它的原始查询的机器可读引用，以及位于 `[0,1]` 的置信度。证据一旦存储
不得再被修改。

**验收。**
- 给定已存储的证据，当重新读取 case 时，则每个字段逐字节一致。
- 给定一个证据标识符，当解析其原始引用时，则该引用给出数据源以及所用的确切查询或选择器。

**验证方式。** TC-0002

<!-- sdd:item id=REQ-0003 stage=specify status=approved derives_from=G-004 priority=P0 -->
### REQ-0003 — Case 状态由只追加事件日志派生

**需求。** 每一次被接受的贡献、状态迁移、策略判定与工具调用都必须追加一条事件。Case 投影
必须能够通过从空状态重放日志来重建，且重建结果必须等于实时投影。

**验收。**
- 给定一个已完成的 case，当把它的事件重放进空投影时，则得到的证据、假设、质疑、动作与
  状态与实时 case 相等。

**验证方式。** TC-0050

<!-- sdd:item id=REQ-0004 stage=specify status=approved derives_from=G-006 priority=P0 -->
### REQ-0004 — 标识符与排序是确定性的

**需求。** 证据、假设、质疑与动作的标识符必须由 case 标识符、产出角色与该角色内的序号
派生——绝不能来自挂钟时间或随机源。API 返回的集合必须具有确定且稳定的顺序。

**验收。**
- 给定相同的夹具输入，当同一 case 运行两次时，则每个生成的标识符与每个集合顺序都完全一致。

**验证方式。** TC-0070

<!-- sdd:item id=REQ-0005 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0005 — 角色边界被强制执行，而不只是写在文档里

**需求。** 每个 Agent 角色必须声明它可以发出的贡献类型，编排器必须拒绝超出发出方声明范围
的贡献。采集类角色不得提出假设；质疑者不得提出假设；只有处置角色可以提议动作。

**验收。**
- 给定某个采集角色返回了假设类贡献，当编排器应用贡献时，则该贡献被拒绝、事件记录该违规、
  且 case 状态不受影响。

**验证方式。** TC-0003

## 4. 信号采集

<!-- sdd:item id=REQ-0010 stage=specify status=approved derives_from=G-006 priority=P0 -->
### REQ-0010 — 每个外部信号都经由端口访问，并具备离线适配器

**需求。** 指标、日志、变更、拓扑、知识与执行必须各自定义为一个端口。每个端口必须具备
无需网络的确定性夹具适配器。适配器集合必须可通过配置选择，无需改动代码。

**验收。**
- 给定夹具配置档，当在禁用网络的条件下运行参考场景时，则场景完成，并产出它所声明的每一
  类证据。

**验证方式。** TC-0010

<!-- sdd:item id=REQ-0011 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0011 — 指标证据识别异常起点与同步变化

**需求。** 指标角色必须针对它查询的每条序列判断其在故障窗口内是否异常，若异常则给出起点
时间戳。它必须报告哪些序列同步变化，且不得陈述序列之间的因果关系。

**塌陷**的序列必须与上升的序列一样被报告为异常。可用性量表跌到零、吞吐量走平、队列被抽干
——这些属于一次故障所能产生的最具诊断价值的信号，而一个只认得"增长"的检测器对它们全都
视而不见。

**验收。**
- 给定一条在已知时刻从 0.2% 阶跃到 18% 的夹具序列，当采集指标证据时，则报告的起点与该
  时刻相差不超过一个采样间隔。
- 给定两条在同一时刻阶跃的序列，当采集证据时，则报告二者同步变化，且摘要中不含因果主张。
- 给定一条从稳定的非零基线跌到零的序列，当采集证据时，则它被报告为异常，并给出下跌的起点。

**验证方式。** TC-0011、TC-0109

<!-- sdd:item id=REQ-0012 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0012 — 日志证据经过聚类且有界

**需求。** 日志角色必须按归一化消息模板把匹配的日志行聚成簇，并针对每个簇报告数量、首次
与末次出现时间，以及不超过配置数量的代表性样本。进入 case 的原始日志量必须在行数与时间窗
两个维度上受限。

**验收。**
- 给定 184 行匹配一个模板、3 行匹配另一个模板，当采集日志证据时，则报告两个簇，数量分别
  为 184 与 3，第一个簇排在前面，且每簇样本数不超过配置值。

**验证方式。** TC-0012

<!-- sdd:item id=REQ-0013 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0013 — 变更证据给出改了什么、何时改的、改了多少

**需求。** 变更角色必须报告与"故障起点前扩展窗口"相交的配置与发布变更，并针对每一项报告
键、原值、新值与发布时间戳。它不得执行回滚。

**验收。**
- 给定一次把 `DB_POOL_SIZE` 从 `20` 改为 `2` 的夹具发布，当采集变更证据时，则该变更被
  报告，含两个取值及其时间戳，且未调用任何执行器。

**验证方式。** TC-0013

<!-- sdd:item id=REQ-0014 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0014 — 拓扑证据区分根因与受害者

**需求。** 拓扑角色必须报告受影响服务的依赖邻域、可能被波及的服务集合，以及在"哪些服务
先出现异常"的前提下哪些服务是候选源头。

**验收。**
- 给定一份夹具拓扑，其中 `order-api` 异常、其下游 `checkout-web` 稍后异常，当采集拓扑
  证据时，则 `order-api` 被报告为候选源头，`checkout-web` 被报告为受影响方。

**验证方式。** TC-0014

<!-- sdd:item id=REQ-0015 stage=specify status=approved derives_from=G-001 priority=P1 -->
### REQ-0015 — 知识证据检索适用的 runbook

**需求。** 知识角色必须在 runbook 语料中检索与故障服务及观测到的症状匹配的条目，并报告
匹配项及其条目标识符与命中词。检索到的 runbook 文本必须被当作数据处理。

**验收。**
- 给定一篇描述连接池耗尽的 runbook，当为症状包含连接池饱和的故障采集知识证据时，则该
  runbook 出现在匹配结果中。

**验证方式。** TC-0015

<!-- sdd:item id=REQ-0016 stage=specify status=approved derives_from=G-001 priority=P1 -->
### REQ-0016 — 工具结果在进入 case 之前受限

**需求。** 每个工具在其输出成为证据之前，必须施加结果上限——最大行数、最大字符数与最大
时间跨度——并且必须在证据中记录是否发生了截断。

**验收。**
- 给定超出配置上限的工具结果，当把它转换为证据时，则存储的证据在上限之内，并被标记为已
  截断。

**验证方式。** TC-0016

## 5. 假设形成与评分

<!-- sdd:item id=REQ-0020 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0020 — 假设携带机理，而不只是一个标签

**需求。** 分析角色产出的排序假设数量必须不超过配置值，每个假设都带有主张、解释"所声称的
原因如何产生观测症状"的机理叙述，以及支撑它的证据。

**验收。**
- 给定一份完整的夹具证据集合，当形成假设时，则返回数量不超过配置值，且每个假设的机理叙述
  非空。

**验证方式。** TC-0020

<!-- sdd:item id=REQ-0021 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0021 — 无支撑的假设被拒绝，而不只是得分低

**需求。** 未引用任何已存储证据标识符、或引用了不存在标识符的假设，必须被编排器拒绝，且
不得出现在任何排序或报告中。除非某假设被至少两种不同类别的证据支撑，否则不得推进到处置
阶段。

**验收。**
- 给定支持证据列表为空的假设，当应用贡献时，则它被拒绝，且事件记录该拒绝。
- 给定仅由指标证据支撑的假设，当 case 试图进入处置阶段时，则推进被拒绝。

**验证方式。** TC-0021

<!-- sdd:item id=REQ-0022 stage=specify status=approved derives_from=G-001 priority=P0 -->
### REQ-0022 — 分数可拆解为具名的加权项

**需求。** 每个假设的分数必须由具名项计算得出——指标吻合度、日志吻合度、变更相关性、拓扑
合理性、历史相似度、处置可验证性——每项带有声明的权重，再减去未消解反证的惩罚。该拆解必须
被存储并随假设一同返回，且各项之和必须等于所报告的分数。

**验收。**
- 给定一个已评分的假设，当把它的拆解求和时，则总和在浮点误差范围内等于所报告的分数。
- 给定声明的各项权重，当求和时，则总和为 1.0。

**验证方式。** TC-0022

<!-- sdd:item id=REQ-0023 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0023 — 反证降低分数并被记录

**需求。** 与某假设矛盾的证据必须被记录到该假设名下，并按每条未消解项声明的惩罚值降低其
分数。随后被解释清楚的反证项必须标记为已消解，并停止贡献惩罚。

**验收。**
- 给定一个无反证时已评分的假设，当附加一条未消解反证时，则分数正好下降声明的惩罚值。

**验证方式。** TC-0023

<!-- sdd:item id=REQ-0024 stage=specify status=approved derives_from=G-006 priority=P0 -->
### REQ-0024 — 排序是全序且确定的

**需求。** 假设排序必须是全序：先按分数降序，再按支持证据类别数降序，最后按标识符升序。
相同输入必须在多次运行与多个进程间产生相同排序。

**验收。**
- 给定两个分数与类别数都相同的假设，当排序时，则标识符较小者排在前面，且每次运行都如此。

**验证方式。** TC-0024

## 6. 对抗评审

<!-- sdd:item id=REQ-0030 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0030 — 质疑是带裁决的结构化记录

**需求。** 质疑角色必须针对每个被审查的假设发出一条质疑，携带假设标识符、质疑类别、质疑
正文、可选的索证描述符列表，以及取值为 `accept`、`accept_with_risk`、`revise` 或
`reject` 的裁决。

**验收。**
- 给定任何进入质疑环节的假设，当质疑运行时，则至少存在一条针对它的质疑记录，其裁决取自
  上述集合。

**验证方式。** TC-0030

<!-- sdd:item id=REQ-0031 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0031 — 质疑者可以强制追加一轮采集

**需求。** 在轮次预算未耗尽的前提下，索证类质疑必须使编排器返回证据采集阶段，并针对被索取
的描述符采集。当预算耗尽时，case 必须在把该索证记录为"未满足"的前提下继续推进，而不是把
它悄悄丢掉。

一条已被某轮采集尝试过、仍未得到回答的索证，不得被再次发出，不得仅凭自身触发又一轮采集，
也不得让某个假设一直停留在非接受裁决上。它仍然必须被记录为未满足，并区分"预算耗尽"与
"本案例中没有来源能回答它"。

**为什么需要第二段。** 没有它，一条无人能答的索证会每轮重试直到预算耗尽；而任何针对**领先**
假设提出该索证的规则，都会把这个假设在余下的整个 case 里按在 `revise` 上——于是 case 什么
也接受不了，并把一个证据本就永远无法了结的问题升级给人。一个没有证据能回应的质疑是否决而
不是质疑（REQ-0101）；而一条没有证据能回应的索证，只是绕远路抵达的同一种否决。

**验收。**
- 给定在第 1 轮（共 3 轮）发出的、索取历史流量对比的质疑，当编排器推进时，则 case 返回
  采集阶段，且下一轮证据中包含回应该描述符的记录。
- 给定同样的质疑发生在最后一轮，当编排器推进时，则 case 继续推进，且未满足的索证出现在
  报告中。
- 给定一条没有来源能回答的索证，当完整流程运行时，则它恰好被索取一次，case 不会为它耗尽
  剩余轮次，仍有解释被接受，且报告把该索证记录为未满足。

**验证方式。** TC-0031、TC-0111

<!-- sdd:item id=REQ-0032 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0032 — 质疑者提出替代解释

**需求。** 除非领先假设已被该 case 采集到的每一类证据所支撑，否则质疑者必须至少给出一个
与当前证据一致的替代解释，并且必须索取能够在该替代解释与领先假设之间做出区分的证据。

**验收。**
- 给定存在饱和证据但尚未检查流量历史的 case，当质疑运行时，则提出"仅仅是流量上涨"这一
  替代解释，并同时索取历史峰值对比。

**验证方式。** TC-0032

<!-- sdd:item id=REQ-0033 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0033 — 质疑者校验时间先后

**需求。** 对于任何把故障归因于某次变更的假设，质疑者必须校验变更时间戳早于异常起点。若
不成立，质疑者必须附加反证，且不得返回 `accept`。

**验收。**
- 给定记录时间晚于异常起点的变更，当质疑运行时，则附加反证，且裁决为 `revise` 或
  `reject`。

**验证方式。** TC-0033

<!-- sdd:item id=REQ-0034 stage=specify status=approved derives_from=G-002 priority=P1 -->
### REQ-0034 — 质疑者挑战"根因与受害者混淆"

**需求。** 当拓扑证据显示受影响服务依赖于另一个更早出现异常的服务时，质疑者必须挑战任何把
原因定位在该受影响服务内部的假设。

**验收。**
- 给定拓扑证据指出某上游服务更早异常，当对归咎于下游服务的假设运行质疑时，则记录一条
  "根因与受害者"类质疑。

**验证方式。** TC-0034

<!-- sdd:item id=REQ-0035 stage=specify status=approved derives_from=G-002 priority=P0 -->
### REQ-0035 — 推进需要显式的接受条件

**需求。** 除非领先假设的质疑裁决为 `accept` 或 `accept_with_risk`、其分数达到配置阈值、
且被至少两类证据支撑——当扩展窗口内发生过任何变更时还必须包含变更证据——否则 case 不得
进入处置阶段。

**验收。**
- 给定裁决为 `revise` 的领先假设，当编排器推进时，则 case 不进入处置阶段。
- 给定窗口内存在变更、而领先假设没有变更证据，当编排器推进时，则 case 不进入处置阶段。

**验证方式。** TC-0035

<!-- sdd:item id=REQ-0036 stage=specify status=approved derives_from=G-002 priority=P1 -->
### REQ-0036 — 分差过小时升级而非猜测

**需求。** 当排名前两位的假设分差小于配置的间距时，case 必须要么索取区分性证据，要么在
轮次预算耗尽时进入人工评审，而不是按领先假设继续推进。

**验收。**
- 给定前两位分差在间距内且仍有预算，当编排器推进时，则发出一条区分性索证。
- 给定同样情形但预算已耗尽，当编排器推进时，则状态变为人工评审。

**验证方式。** TC-0036

## 7. 处置、策略与审批

<!-- sdd:item id=REQ-0040 stage=specify status=approved derives_from=G-003 priority=P0 -->
### REQ-0040 — 动作是完整提案，而不是命令

**需求。** 每个拟议动作必须携带标题、它将调用的工具与带类型的参数、取值为 `low`、
`medium` 或 `high` 的风险等级、前置条件、回滚动作，以及可确认其效果的验证步骤。缺少回滚
或验证的动作，不得以高于低风险的等级被提议。

**验收。**
- 给定参考场景，当处置运行时，则"恢复连接池大小"动作被提议，风险为 `medium`，带有恢复
  原值的回滚，以及指明错误率序列的验证。

**验证方式。** TC-0040

<!-- sdd:item id=REQ-0041 stage=specify status=approved derives_from=G-003 priority=P0 -->
### REQ-0041 — 策略引擎按白名单放行，其余一律拒绝

**需求。** 策略引擎必须依据服务、配置键、工具与取值范围的白名单评估每一个动作，并拒绝
任何不在白名单内的动作。任意 shell 执行、自由形式 SQL、资源删除与跨服务批量操作必须被
无条件拒绝。

**验收。**
- 给定目标服务不在白名单内的动作，当评估时，则被拒绝，且理由指明被违反的规则。
- 给定工具为 shell 调用的动作，当评估时，则无论审批状态如何都被拒绝。

**验证方式。** TC-0041

<!-- sdd:item id=REQ-0042 stage=specify status=approved derives_from=G-003 priority=P0 -->
### REQ-0042 — 中高风险动作停在审批门

**需求。** 风险等级为 `medium` 或 `high` 的动作必须使 case 进入等待审批状态，且在记录
审批决定之前不得执行。低风险动作在策略允许时可以自动执行。

**验收。**
- 给定一个中风险动作，当编排器推进时，则状态为等待审批，且未调用任何执行器。

**验证方式。** TC-0042

<!-- sdd:item id=REQ-0043 stage=specify status=approved derives_from=G-003 priority=P0 -->
### REQ-0043 — 执行前的一刻重新校验策略

**需求。** 执行器必须在审批之后、以执行时刻动作的实际形态重新评估策略；若动作或策略发生
了变化以致不再被允许，必须拒绝执行。

**验收。**
- 给定一个已审批但审批后参数被改动的动作，当尝试执行时，则被拒绝，且该拒绝被记录。

**验证方式。** TC-0043

<!-- sdd:item id=REQ-0044 stage=specify status=approved derives_from=G-003 priority=P0 -->
### REQ-0044 — 检索到的内容不能成为指令

**需求。** 从日志、提交信息、runbook、工单或任何其他外部来源检索到的内容，只能作为证据
载荷进入系统。它不得改变 Agent 角色声明、工具选择、策略或审批状态。执行器只接受带类型的
动作，且必须拒绝任何由检索文本拼装而成的动作。

**验收。**
- 给定一行日志包含"指示系统执行重启"的文本，当处理该 case 时，则不会从该文本产生任何
  动作，也不会有任何策略规则发生变化。

**验证方式。** TC-0044

<!-- sdd:item id=REQ-0045 stage=specify status=approved derives_from=G-003 priority=P0 -->
### REQ-0045 — 审批与执行留有审计

**需求。** 每一次审批决定都必须记录决定内容、决策者身份、时间戳与备注。每一次执行都必须
记录动作、结果、耗时与目标系统的响应。二者都必须出现在事件日志与报告中。

**验收。**
- 给定一个已审批并已执行的动作，当读取审计轨迹时，则其中包含审批人身份、决定与执行结果。

**验证方式。** TC-0045

<!-- sdd:item id=REQ-0046 stage=specify status=approved derives_from=G-003 priority=P1 -->
### REQ-0046 — 被拒绝的动作走向报告，而非静默终止

**需求。** 当审批被拒绝时，case 必须继续推进到报告阶段，并记录该拒绝、其理由以及未执行的
动作。

**验收。**
- 给定一次被拒绝的审批，当编排器推进时，则 case 到达报告阶段，且报告中包含被拒绝的动作
  及其理由。

**验证方式。** TC-0046

<!-- sdd:item id=REQ-0064 stage=specify status=approved derives_from=G-006 priority=P1 -->

**验收。**

  以及针对该中风险动作的审批控件。

<!-- sdd:item id=REQ-0095 stage=specify status=approved derives_from=G-007 priority=P1 -->
### REQ-0095 — 以带版本的 release 发布，并附 linux/amd64 镜像

**需求。** 打上版本标签时，必须发布一个 GitHub release，其中携带可运行于 `linux/amd64`
的容器镜像，以及同平台的、带校验和的二进制文件。镜像必须由自动化流水线从被打标签的提交
构建，而不是人工上传；必须标注它来自哪个提交；并且必须在 release 发布之前通过 compose
栈所依赖的同一个健康检查。

release 不得从一棵通不过交付门禁的树上发布：能够发布的版本，按定义就是其规格树已封存、
已追溯、已测试的版本。

**验收。**
- 给定一个匹配 `v*` 的标签，当流水线运行时，则它构建 `linux/amd64` 镜像、启动它、等待
  `/healthz`、以版本标签与提交 SHA 两种标签把镜像推送到镜像仓库，并创建一个 release，
  其资产包含这些二进制文件、一个可加载的镜像 tar 包与一个 `SHA256SUMS` 文件。

镜像 tar 包与镜像仓库并不重复。仓库中的包可能是私有的、可能要求读者并不具备的登录凭据、
也可能被清理掉；而挂在 release 上的资产，任何能看到该 release 的人都能下载，并用
`docker load` 加载。release 必须在没有镜像仓库访问权的情况下依然可用。
- 给定一棵通不过 `sddctl gate --stage deliver` 的树，当流水线运行时，则它在发布任何东西
  之前就失败。
- 给定一位能运行工作流、但无法推送标签的维护者，当他们带上版本号手动启动流水线时，则它
  产出同样的 release，并自行创建该标签。

之所以要有手动入口，是因为"推送标签"与"运行工作流"这两项权限是分别授予的；而一个只有
能推标签的人才切得出来的 release，对另一些维护者来说等于切不出来。两个入口跑的是同一个
job，谁都无法跳过任何一道门禁。

**验证方式。** TC-0092

<!-- sdd:item id=REQ-0096 stage=specify status=approved derives_from=G-001 priority=P1 -->
### REQ-0096 — 基于 Prometheus HTTP API 的在线指标适配器

**需求。** 指标端口必须具备一个查询 Prometheus HTTP API 的在线适配器，返回与夹具适配器
相同的 `Series` 形状，使端口之上的任何代码都无法分辨是哪个适配器提供的数据。它必须施加
端口的上限，必须标记截断而不是静默丢弃采样点，并且必须以一个带类型的错误失败，使采集器
能把它记为"降级的数据源"，而不是一次崩溃。

Prometheus 响应中出现 `NaN`、陈旧标记，或某序列没有任何采样点时，必须被当作"证据缺失"，
而不是零值：读数为零与没有读数支持的是不同的结论。

**验收。**
- 给定一份录制的 `query_range` 响应，当适配器映射它时，则所得序列在形状、顺序与单位上与
  等价的夹具序列一致。
- 给定采样点数超过上限的响应，当适配器映射它时，则序列被截断且截断被报告。
- 给定一个不可达的端点，当采集器查询它时，则采集器记录一个降级数据源，调查继续进行。

**验证方式。** TC-0100、TC-0101

<!-- sdd:item id=REQ-0097 stage=specify status=approved derives_from=G-001 priority=P1 -->
### REQ-0097 — 基于容器运行时的在线日志适配器

**需求。** 日志端口必须具备一个在线适配器，从容器运行时读取容器日志，解复用运行时的流
分帧，按查询的关键词与时间窗过滤，并施加端口的上限。

**验收。**
- 给定一段多路复用的运行时日志流，当适配器读取它时，则 stdout 与 stderr 记录连同正确的
  流标签与时间戳一并被还原。
- 给定带关键词与时间窗的查询，当适配器检索时，则只返回同时匹配所有关键词、且落在时间窗
  内的行，并施加上限与标记。

**验证方式。** TC-0102

### REQ-0098 — 适配器的选择属于配置，且离线仍是默认

**需求。** 为每个端口提供服务的适配器必须在启动时由具名 profile 选定。默认 profile 必须
是夹具 profile。测试套件中的任何一个测试都不得依赖网络访问、容器运行时或 Prometheus
实例才能通过。

**验收。**
- 给定没有任何配置，当系统启动时，则每个端口都由其夹具适配器提供服务。
- 给定完整测试套件，当它在无网络环境下运行时，则它通过。

这条需求正是在线适配器可以安全加入的原因。一组可能悄悄变成默认的适配器，会让系统其余部分
所依赖的确定性（REQ-0090）变成取决于环境的东西。

**验证方式。** TC-0103

### REQ-0099 — 正确性不得依赖于"不信任某个特定解释"

**需求。** 故障目录必须至少包含一个"最响亮的证据并非成因"的样例，以及至少一个"正确答案
恰恰是参考场景教系统去否定的那个解释"的样例。对抗流程必须在这两个样例上都得出所声明的
根因。

**为什么这是一条需求而不是测试细节。** 参考场景 C1 的取胜方式，正是把两个解释从排序中降
下来，`sig-traffic-surge` 是其中之一。一个学到"领先的解释就是错的"或"流量从来不是原因"的
系统，能在 C1、C2、C3 上拿满分，却什么也没学会。质疑者的价值在于它会**区分**；而只有存在
一个"它必须选择不反对"的样例时，这种区分能力才算被证明。

**验收。**
- 给定一个样例，其日志量压倒性地匹配某个签名，而具有区分力的指标与变更证据却否定它；当
  完整流程运行时，则所声明的根因被接受，而那个响亮的签名不被接受。
- 给定同一个样例，当流程运行时，则被接受的原因是 `sig-traffic-surge`——也就是 C1 所降级的
  解释之一——从而证明结论是由证据引导的，而不是一种固定的偏见。

**验证方式。** TC-0104

<!-- sdd:item id=REQ-0100 stage=specify status=approved derives_from=G-005 priority=P1 -->
### REQ-0100 — 同一端口背后的模型推理器

**需求。** 推理器端口必须具备一个基于模型的适配器，它从目录中选择签名并把证据绑定到其上。
它不得发明目录之外的主张，也不得提供分数：打分保持确定性，由适配器所绑定的证据计算得出
（ADR-007）。

每个响应都必须被当作不可信的结构化数据。引用了快照中不存在的证据标识符的假设必须被丢弃；
不在目录中的签名标识符必须被丢弃；落在封闭集合之外的裁决必须被丢弃。格式错误或不可达的
服务商必须表现为带类型的错误，绝不能表现为静默的空结果——空假设列表意味着"没有任何匹配"，
而服务商故障不得冒充这个含义。

**验收。**
- 给定一份录制的服务商响应，它选择了某个目录签名并给出快照中的证据标识符，当适配器映射它
  时，则所得假设携带的是由确定性打分器计算的分数，而不是服务商给出的分数。
- 给定一份引用了未知证据标识符、未知签名或非法裁决的响应，当适配器映射它时，则这些条目被
  丢弃，其余条目保留。
- 给定一个不可达的服务商，当适配器被调用时，则它返回带类型的错误，而不是空结果。

**验证方式。** TC-0105、TC-0106

### REQ-0101 — 告警落在受害者身上时，必须找到它上游的原因

**需求。** 当告警服务位于某个更早异常的服务的下游时，调查必须得出定位在上游服务的那个解释，
且它提议的处置必须指向该上游服务，而不是发出告警的那个服务。

`source_vs_victim` 质疑必须挑战那些把原因定位在受害者内部的解释，并且**不得**挑战一个
本就把原因归于上游的解释。一个没有任何证据能够回应的挑战，是否决，而不是质疑。

**验收。**
- 给定一个 case，其告警指向的服务依赖于一个更早异常的上游服务；当完整流程运行时，则被接受
  的解释是定位在上游的那个，且拟议动作指向该上游服务。
- 给定同一个 case，当质疑者运行时，则 `source_vs_victim` 出现在所提出的质疑之中——该规则
  必须被端到端地执行，而不只是被孤立地测过。

**验证方式。** TC-0107

<!-- sdd:item id=REQ-0102 stage=specify status=approved derives_from=G-001,G-002 priority=P0 -->
### REQ-0102 — 晚于症状发生的变更不可能解释该症状

**需求。** 若某解释所归咎的变更发生在它声称导致的症状起点**之时或之后**，则无论其余证据
吻合得多好，都必须以时序理由拒绝它，并把该时序关系记录为反证。

**为什么这需要一个专属样例。** "我们发布了，然后它坏了"是故障现场最唾手可得的解释，而且
它能通过其他每一项检查：变更是真的，症状是真的，签名的其余要求也都可能匹配。唯一能反驳它
的就是先后顺序。一个没有任何样例检验该顺序的目录，等于让这项检查始终未经证明。

**验收。**
- 给定一个 case，其中某个变更匹配了某解释的要求、却发生在症状起点之后；当完整流程运行时，
  则该解释被拒绝，被接受的原因是其变更早于起点的那一个。
- 给定同一个 case，当质疑者运行时，则 `temporal_order` 出现在所提出的质疑之中。

**验证方式。** TC-0108

### REQ-0103 — 参考场景的首轮错误必须是"证据齐备"的

**需求。** 凡是"质疑者被记功为找到正确答案"的样例，都必须在第一轮采集结束时得到一个既
**错误**又**完备**的领先解释：其签名所声明的每一条证据要求，都必须被当时已采集的证据满足；
且它对第二名的分差必须大于"分差过小"间距。随后的对抗轮次必须以**记录在案的反证**把它挤
下来，而不能只是分数上压过它。

各样例用来反驳它的那种观测必须彼此不同。若目录中每个错误的首轮答案都倒在同一种检查之下，
那证明的是那一种检查，而不是对抗式复核。

**为什么这是一条需求而不是测试细节。** 一个"因为证据缺失而错"的首轮结论把标准定得太低：
质疑者只需索要一件还没人查过的东西就取胜了，这证明的是采集是否周全，而不是对抗式复核。本
系统主张的东西更强——一个证据充分、把握十足、自洽成立的答案，仍然可能是错的，而结构化的反对
正是把它找出来的手段。只有当场景的第一个答案"要什么有什么"时，这一主张才谈得上被检验。

分差这个条件不是装饰。其中两个样例此前第 1 轮的领先幅度只有 0.01 与 0.03——那是一次恰好
落错的掷硬币，把这样的排序纠正过来，对质疑者什么也证明不了。值得被推翻的错误，是一个细致
的推理者会有把握地持有的错误。

**验收。**
- 给定参考场景在一轮采集后停下；当把领先假设的签名与已采集证据做匹配时，则没有任何要求
  处于未匹配状态，且领先者对第二名的分差大于"分差过小"间距。
- 给定同一场景完整运行；当 case 关闭时，则被接受的原因与首轮领先者不同，且首轮领先者携带
  反证，而不只是名次下滑。

**验证方式。** TC-0110

### REQ-0104 — 每一种策略在任何产出结果的入口都可选择

**需求。** 每一个会产出可比较结果的入口——服务、单案例运行器、评测运行器——都必须为系统拥有的
**每一个**策略端口接受同一套选择方式，并且必须记录每个结果由哪个适配器产出。

这些端口是**各自独立**可选的。推理与规划是两种不同的判断；一个同时拨动两者的开关，会让它们
各自的贡献在"本系统专为测量它们而存在"的那个地方变得无法分离。

**为什么这是一条需求。** ADR-002 声称"换成模型不改变任何契约、任何状态迁移、任何存储结构"。
这个声称值多少，取决于它能被拿什么来检验。如果选择方式只有服务这一个入口，参考场景就无法
通过模型适配器运行，两种策略也就无法对照——于是本项目最核心的架构主张从外部**不可证伪**，
而默认值的选择就只建立在论证之上，而不是建立在测量之上。

**验收。**
- 给定参考场景，当它依次通过每个适配器运行时，则两者都能跑完，且 case 记录了产出结果的
  适配器。
- 给定评测运行器，当它针对某个适配器运行时，则每一行结果都标明该适配器。

**验证方式。** TC-0112

<!-- sdd:item id=REQ-0105 stage=specify status=approved derives_from=G-005 priority=P0 -->
### REQ-0105 — 每个策略端口的适配器都对同一份契约负责

**需求。** 对每一个策略端口，它的**所有**适配器都必须通过同一套契约测试；该测试断言编排器
所依赖的性质，与产出它的策略无关。

对推理器端口而言：每个假设引用的证据都存在于快照中、命名的签名都存在于目录中、且带有机理；每条
质疑都指向一个被审查过的假设并带有闭集内的裁决；每条索证都带有描述符与类别。服务商失败必须
以错误浮现，**不得**被报告为空结果。

**为什么这是需求而不是测试细节。** ADR-002 把这项测试列为"双适配器"决策的后果之一，而它
从未被写出来。一个两个适配器只是"能编译通过"的接口不是契约，那只是形状。编排器真正依赖的
是行为性质；在两个适配器都被这份契约约束之前，"换适配器什么都不变"只是一句关于代码的断言，
没有人核对过。

对规划器端口而言：方案中的每条序列要么是数据源提供的，要么被作为"已丢弃"报告出来；一份什么
也不会采集的方案会被确定性方案取代；服务商失败以错误浮现，而不是浮现为一份空方案。

**验收。**
- 给定每个端口的每个适配器，当该端口的契约测试套件对它运行时，则全部性质对它们都成立。
- 给定一个服务商不可达的适配器，当向它索要假设或方案时，则返回错误而不是空结果。

**验证方式。** TC-0113、TC-0117

<!-- sdd:item id=REQ-0106 stage=specify status=approved derives_from=G-005 priority=P1 -->
### REQ-0106 — 评测把每个数字都归因到某个推理器

**需求。** 评测报告必须在每一行结果与每一行汇总中，把**每一个**策略适配器与模式并列记录，
从而使两次运行之间的差异**可归因于策略**，而不是被假定为策略造成的。

**验收。**
- 给定一次评测运行，当报告产出时，则每一行汇总都标明模式、推理器与规划器，并附带样本量。
- 给定一次"固定一个策略、变动另一个策略"的运行，当汇总分组时，则每一种组合各占一行，而不是
  与另一种被平均在一起。

**验证方式。** TC-0114

<!-- sdd:item id=REQ-0107 stage=specify status=approved derives_from=G-001,G-005 priority=P0 -->
### REQ-0107 — "去看什么"是本系统自己做出的决定

**需求。** triage 必须产出一份调查方案——时间窗与要运行的角色；collection 必须产出一份查询
方案——从数据源**实际提供**的东西中，点名要检索的序列与日志词。两者都必须经由一个策略端口
达成：默认适配器是确定性的，备选适配器由模型支撑；且两者都必须作为**决定**记录进 case 时间线。

**为什么这是一条需求。** 今天的 collection 什么也没决定：指标采集器向每个数据源索要它提供的
一切，并全部分析。第 1 轮看了什么——在本系统里它决定了首轮错误，因而也决定了质疑者要推翻
什么（REQ-0103）——是**夹具**的性质，而不是任何 Agent 的性质。这使得整个流程中最有后果的那个
选择，恰恰是没有任何角色为之负责的那一个。

**验收。**
- 给定参考场景，当 triage 与 collection 运行时，则各自产出的方案被记录在 case 上，并点名了
  实际使用的时间窗、角色、序列与日志词。
- 给定一份点名了任何数据源都不提供的序列的查询方案，当 collection 运行时，则该条被丢弃，
  方案的其余部分照常执行。
- 给定一个什么也没返回的规划器，当 collection 运行时，则使用确定性方案——因为一个失败的策略
  不得让调查失明。

**验证方式。** TC-0115

<!-- sdd:item id=REQ-0108 stage=specify status=approved derives_from=G-002,G-004 priority=P0 -->
### REQ-0108 — 处置与验证保持确定性

**需求。** remediation 与 verification 两个角色**不得**经由模型支撑的策略。remediation 必须
产出一个取自目录的类型化动作；verification 必须通过比较信号取值来判定恢复。

**为什么这是需求而不是遗漏。** ADR-008 偏离了目标文档——后者为每个角色都指定了 system prompt
——而一次偏离应当写进规格、可以被拿来争论，而不是躺在两份文件之间的沉默里。策略引擎只能对它
能解析的东西设门，且 REQ-0041 禁止 Agent 自行编写 shell 与 SQL；因此在执行器之前插入一个
自然语言环节，会抹掉审批门赖以成立的那个保证。验证则是算术：一个**能够**与比较结果不一致的
策略，会把恢复结论从证据变成意见。

**验收。**
- 给定任何已配置的策略，当 remediation 运行时，则所提议动作的工具与参数均来自目录模板，并
  原样通过策略校验。
- 给定任何已配置的策略，当 verification 运行时，则恢复判定仅凭记录在案的前后取值即可复现。

**验证方式。** TC-0116
