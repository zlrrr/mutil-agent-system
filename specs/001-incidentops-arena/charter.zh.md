# IncidentOps Arena — 目标章程

## 1. 问题

当生产服务出现劣化时，值班人员是在时间压力下做证据工作：看告警、关联指标、grep 日志、
查最近一小时发布了什么，并判断眼前这个服务究竟是原因还是受害者。真正代价高昂的故障，
不是那种没人去看的，而是那种有人看了、找到了一个说得通的故事、然后就停下来了的。

单个语言模型会忠实地复现这种失效模式。给它一份满是 `connection timeout` 的日志，它会
自信地讲出一个数据库宕机的故事——因为第一个自洽的故事就是它讲出来的那个。在单 Agent
循环里，没有任何结构性的东西强迫它去问：*还有什么别的原因也会产生这些证据？*

由此得出两件事。第一，证据采集应当按来源拆分，这样就没有单一上下文窗口来决定"存在哪些
证据"。第二，必须有人被"付钱来反对"——而且这个角色需要真实权力，而不是一句措辞礼貌的
提醒。

## 2. 结果陈述

运维人员收到告警后，无需离开同一个界面，就能看到：哪个 Agent 采集了哪些证据、带有逐项
分数拆解的根因假设排序、对抗评审者提出的质疑、这些质疑逼出的补充证据、次优解释为何被
排除、一份经过风险分级并停在审批门前的处置方案，以及——在他们批准之后——指标确实回落的
验证结果。界面上的每一条主张都携带一个证据标识符，可以回溯到其背后的原始查询。

## 3. 目标

<!-- sdd:item id=G-001 stage=charter status=approved derives_from=CON-005,CON-011 priority=P0 -->
### G-001 — 根因是站得住脚的，而不只是被产出来的

**陈述。** 系统报告的每个假设都绑定到来自具名数据源的已存储证据，携带可拆解的置信度分数；
若不满足，编排器直接拒绝该假设。

**度量。** 没有任何假设能在不具备至少两类不同证据的情况下进入报告；每个分数都能渲染为
逐项拆解，且各项之和等于所报告的值。

**优先级。** P0

**非目标边界。** 该目标并不要求首位假设在任何输入下都正确；它要求的是：错误的假设必须
显式地表现为缺乏支撑。

<!-- sdd:item id=G-002 stage=charter status=approved derives_from=CON-005 priority=P0 -->
### G-002 — 对抗评审者拥有真实权力

**陈述。** 一个专职的质疑角色可以强制追加证据采集、降级或否决领先假设、并阻止流程推进到
处置阶段。它的反对意见是结构化记录，而不是附在报告末尾的一段话。

**度量。** 在参考场景中，质疑者改变了结果：它至少强制了一轮额外采集，且质疑后的排序与
质疑前不同。

**优先级。** P0

**非目标边界。** 质疑者不提出自己的根因；它只负责挑战、索证与否决。

<!-- sdd:item id=G-003 stage=charter status=approved derives_from=CON-009,CON-012 priority=P0 -->
### G-003 — 处置经过风险分级并设有门禁

**陈述。** 每个提议动作都携带风险等级、回滚方案、前置条件与验证步骤。只读工具自主运行；
任何高于低风险等级、且会改变目标系统的动作，都会让状态机停下来，直到人工做出决定。

**度量。** 没有记录在案的审批，中/高风险动作无法执行；绕过门禁的尝试会被策略引擎拒绝并
记录，且该拒绝是在执行前的一刻强制生效，而不是在规划阶段。

**优先级。** P0

<!-- sdd:item id=G-004 stage=charter status=approved derives_from=CON-011 priority=P0 -->
### G-004 — 恢复经过验证，调查过程可重放

**陈述。** 已批准的动作执行后，系统会重新查询触发该故障的信号，并记录它们是否恢复。整个
调查过程——每次 Agent 调用、工具调用、状态迁移与策略判定——都能仅凭事件日志重建。

**度量。** 从事件日志重新生成的最终报告，与实时产出的报告逐字段一致。

**优先级。** P0

<!-- sdd:item id=G-005 stage=charter status=approved derives_from=CON-005,CON-007 priority=P1 -->
### G-005 — 多 Agent 流程可被证明优于单 Agent 基线

**陈述。** 相同的故障场景在三种模式下运行——单 Agent、无质疑的多 Agent、以及完整流程——
使用相同的证据，且对比结果是算出来的，不是宣称出来的。

**度量。** 一条评估命令针对至少三个可复现故障样例，逐模式输出 top-1 准确率、top-3 覆盖率、
证据类别完整度与被质疑者纠正的假设数量。

**优先级。** P1

**非目标边界。** 该结论只针对这套基准，而非泛化到一般生产 SRE 工作；报告会在每个数字旁边
标注样本量。

<!-- sdd:item id=G-006 stage=charter status=approved derives_from=CON-007 priority=P0 -->
### G-006 — 一个完整业务场景端到端可复现运行

**陈述。** 订单 API 连接池耗尽场景从告警接入一直跑到签发报告，过程确定，无需网络访问，
也无需模型服务。

**度量。** 一条命令即可复现该场景；重复运行产生完全相同的假设排序、完全相同的证据标识符
与完全相同的报告内容。

**优先级。** P0

<!-- sdd:item id=G-007 stage=charter status=approved derives_from=CON-008 priority=P1 -->
### G-007 — 以容器镜像交付，并附带双语手册

**陈述。** 交付物是一个容器镜像，外加一套可拉起 API、控制台与演示环境的 compose 栈，并
配有中英双语用户手册，覆盖安装、演示走查、API、配置与故障排查。

**度量。** 一位从未见过本仓库的读者，仅凭手册即可拉起演示并驱动参考场景。

**优先级。** P1

<!-- sdd:item id=G-008 stage=charter status=approved derives_from=CON-006,CON-010 priority=P0 -->
### G-008 — MVP 离线通过全部既定测试

**陈述。** 当所有既定测试用例在无网络、无凭据、无外部服务的条件下执行并通过，且治理树已
封存、无漂移时，里程碑 M1 达成。

**度量。** 在网络隔离环境中，`go test ./...` 与 `sddctl validate` 均以零码退出。

**优先级。** P0

## 4. 非目标

| # | 排除项 | 原因 | 何时重新考虑 |
|---|---|---|---|
| N1 | 对真实生产系统的自动修复 | 审批门本身就是产品，而不是需要被移除的障碍 | 本系统永不；那需要一套不同的风险模型 |
| N2 | 云与 SaaS 连接器（Datadog、PagerDuty、Kubernetes、云 API） | 每一个都会引入凭据与在线依赖，从而毁掉演示 | 确定部署目标并有凭据管理方案时 |
| N3 | 向量数据库与知识图谱 | 知识库规模小到精确检索足矣；向量库只会多一个服务而不改变任何结论 | runbook 语料超过数百篇时 |
| N4 | 给 Agent 任意 shell 或自由形式 SQL | 影响半径无界，且没必要——每个真实动作都能表达为带类型的工具调用 | 永不 |
| N5 | 面向全部运维工作的通用 SRE 助手 | 铺得太宽会稀释掉核心的对抗机制 | 对抗流程在窄范围内被验证之后 |
| N6 | 多租户认证与授权 | 单操作者演示范围；现在加入只会遮蔽流程本身 | 系统部署到单一可信操作者之外时 |

## 6. 对原始项目说明的范围修正

原始说明（`project.md`）是问题陈述与 Agent 角色划分的来源，二者均予保留。其中三项决策在
此依据该说明自身授予的修订权限做出修正。

| # | 原说明 | 本章程 | 原因 |
|---|---|---|---|
| A1 | Python + FastAPI 后端，LangGraph 编排 | Go，仅标准库 | 由项目负责人指定。同时服务于 CON-007 与 CON-008：单个静态二进制、构建期无依赖树需要解析、且编排器的状态机是显式代码而非框架配置 |
| A2 | Next.js + TypeScript 控制台 | 内嵌于二进制的服务端渲染控制台 | 控制台的职责是让 Agent 时间线与证据链可见。引入构建工具链与第二个运行时只会增加交付风险，不会增加可见性 |
| A3 | 以在线 Prometheus、Docker 日志与 git 作为一等数据源 | 同样的数据源置于端口之后，并以确定性夹具适配器作为默认 | CON-007。演示与测试套件不能依赖某个采集目标是否健康；在线适配器保留，由配置选择 |

原说明中有两项决策明确保留：第 8 节的 Agent 角色划分，以及第 12.1 节的证据加权评分模型。
两者在意图不变的前提下带入需求。
