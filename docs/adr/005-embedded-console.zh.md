# ADR-005 — 采用服务端渲染的内嵌控制台，而非前端应用

**状态。** accepted

**日期。** 2026-08-05

## 背景

原说明提议使用 Next.js 与 TypeScript。按照 REQ-0065，控制台的职责窄而具体：在一个屏幕上
实时呈现 Agent 时间线、证据链、分数拆解、质疑与审批门。

那是一个以读为主的视图，带一个交互控件（批准或拒绝）和一路实时推送。它不是一个应用。

独立前端的代价是：镜像里多一个运行时、构建期多一次包安装、CI 中多一个构建步骤，以及两个
可部署物之间的版本漂移面——而这一切换来的，是一个全部意义就在于"看得清楚"的视图。

## 决策

我们将用同一个二进制、通过 `html/template` 提供控制台，资源以 `embed` 内嵌，并用
server-sent events 推送更新。没有 JavaScript 框架，没有构建步骤，没有外部资源路径。

## 后果

### 正面

- 一个制品、一个端口、一个版本。`docker run` 然后打开浏览器即可。
- 构建期无需网络访问，从而让 REQ-0092 可满足。
- 视图渲染所用的 case 投影与 API 提供的是同一份，因此控制台与 API 不可能各说各话。
- Server-sent events 在标准库之上只需几十行，并天然支持按序号游标重连（ARC-012）。

### 负面

- 丰富交互——过滤、图形缩放、可拖拽时间线——会很费力。但这些都不是需求。
- 样式与布局是手写 CSS。
- 期待精致单页应用的评审者，可能会觉得控制台不如其背后的系统那样完成度高。

### 中性

- API 独立于控制台且有完整文档，因此日后仍可在不改动服务端的前提下另做前端。

## 已考虑的备选方案

| 备选方案 | 它的吸引力 | 为何落选 |
|---|---|---|
| Next.js 单页控制台 | 交互更丰富；原说明这么提议 | 为一个以读为主的视图引入第二套工具链与运行时；构建期网络访问与 REQ-0092 冲突 |
| 服务端渲染 + 一小段原生脚本做实时更新 | 折中方案 | 这正是最终选择——那"一小段脚本"就是 SSE 订阅者，几十行，无框架 |
| 只做终端界面 | 完全没有 Web 表面 | REQ-0065 要求一个评审者能看的屏幕；终端并不适合承载证据面板 |

## 重新评估触发条件

出现服务端渲染无法承载的交互需求——实时图形操作，或带有大量客户端状态的运维工作流。
