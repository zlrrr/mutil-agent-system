# ADR-006 — 采用声明式故障签名与样例目录，而非硬编码场景

**状态。** accepted

**日期。** 2026-08-05

## 背景

在本系统的生命周期中有两样东西必然增长：推理器能识别的故障签名集合，以及评估所针对的场景
集合。REQ-0082 要求新增样例时不触碰 Agent 代码。

如果二者之中任何一个写在 Go 源码里，增长就意味着重新编译；更糟的是，意味着新增场景的人
必须理解 Agent 内部。它还会让过拟合变得不可见：写在使用它的函数内部的签名，与一个特例
毫无区别。

还有一个更隐蔽的风险。如果某个场景的夹具数据与识别它的签名是在代码里一起写出来的，测试
可能仅仅因为两者编码了同一个假设而通过。把它们保持为分离的数据文件、由同一套通用机制加载，
才能让这种耦合在评审中显形。

## 决策

我们将把二者都表达为内嵌的 JSON 数据：

- **故障签名**声明所需的证据模式、机理叙述模板、能够反驳它的区分性证据，以及逐项评分提示。
- **故障样例**声明告警、夹具信号集合（序列、日志行、变更、拓扑）、预期根因与预期处置。

两者都内嵌进二进制，由通用代码加载。新增任一者都是一次数据变更。

## 后果

### 正面

- 新场景是一次可评审的数据 diff；评估无需任何代码改动即可纳入它。
- 签名覆盖面可审计——读一遍目录就能看出系统能识别什么、不能识别什么，而这恰恰是评审者
  应当能够检查的。
- 同一份夹具数据同时驱动单元测试、端到端场景与评估，因此三者不可能漂移。
- 过拟合可度量：签名与样例是分开的文件，因此"只匹配一个样例"的签名一眼可见。

### 负面

- 声明式模式语言的表达力不如代码。需要真正新颖匹配逻辑的签名，得先扩展匹配器，那是一次
  代码变更。
- 多出两套需要编写文档、需要校验、需要各自错误信息的模式。
- JSON 不适合承载长篇机理叙述；因此叙述是精简且模板化的。

### 中性

- 该目录也正是日后模型适配器可以**提议**新增条目的自然位置，从而保留了扩展路径。

## 已考虑的备选方案

| 备选方案 | 它的吸引力 | 为何落选 |
|---|---|---|
| 把签名写成 Go 函数 | 表达力完整；无需模式 | 扩展需重新编译，而且在评审中签名与特例无法区分 |
| 场景仅作为测试夹具 | 对测试来说最简单 | 评估与演示将需要各自的副本，而副本会漂移 |
| 从磁盘加载外部数据文件 | 无需重新构建即可编辑 | 与 ARC-014 的"单一自包含制品"冲突；文件缺失会变成一种运行期失败模式 |

## 重新评估触发条件

出现一条不扭曲模式语言就无法表达的签名，或者目录大到不再适合内嵌。
