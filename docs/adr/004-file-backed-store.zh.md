# ADR-004 — 采用文件只追加存储，而非数据库

**状态。** accepted

**日期。** 2026-08-05

## 背景

原始说明提议首期 SQLite、二期 PostgreSQL。ADR-003 已经把持久化归约为单一访问模式：向某个
case 追加事件，并按序读取该 case 的事件。任何需求中都不存在连接查询、二级索引、并发写入
或跨 case 查询。

CON-008 使得"内嵌 SQL 引擎"成为一个需要论证的决策——纯 Go 的 SQLite 驱动是体量很大的
依赖，其编译时间会盖过整个构建的其余部分——而外部 PostgreSQL 又会增加一个演示必须拉起、
测试必须 mock 或启动的服务。

## 决策

我们将定义一个 `Store` 端口，暴露 case 索引以及事件的追加与区间读取，并实现两次：内存
适配器（测试与默认演示档），以及文件适配器——每个 case 一份 JSON Lines 日志，配一个原子
写入的 case 索引。

## 后果

### 正面

- 零依赖、零服务；`go test ./...` 不需要任何夹具数据库。
- 落盘格式就是事件格式，因此一个 case 可以用 `cat` 查看、可以做 diff——评审演示运行时很
  有用。
- 追加与扫描恰好是文件系统擅长的；按 case 分文件让写竞争根本不存在。
- 该端口足够小，因此增加数据库适配器是一次可控的补充。

### 负面

- case 索引更新与事件追加之间没有事务保证；索引在启动时由目录重建，因此它是派生的而非
  权威的。
- 除扫描外没有查询能力。跨多个 case 的报表需要把它们全读一遍。
- 保留策略靠人工：单 case 内由 ARC-011 限界，但旧 case 文件不会被自动回收。

### 中性

- 持久性成为按配置档做出的部署选择，而不是设计承诺。

## 已考虑的备选方案

| 备选方案 | 它的吸引力 | 为何落选 |
|---|---|---|
| 内嵌 SQL 引擎 | 熟悉；可查询；原说明也这么提议 | 对一个没有关系型访问模式的负载而言违背 CON-008；驱动的构建成本超过整个服务 |
| 外部 PostgreSQL | 更贴近生产形态；原说明的二期方案 | 演示必须启动、测试必须提供的一个服务。换来的持久性保证是演示并不需要的 |
| 纯内存 | 可能的最简方案 | 一次重启就会丢掉评审者刚看完的演示运行，而 REQ-0053 的重放将无从重放 |

## 重新评估触发条件

出现跨 case 分析需求、单 case 并发写入需求，或扫描无法支撑的保留策略需求。
