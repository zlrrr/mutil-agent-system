# ADR-001 — 以 Go 与标准库作为实现基座

**状态。** accepted

**日期。** 2026-08-05

## 背景

原始说明提议使用 Python + FastAPI 以及某个 agent 图框架。项目负责人改为指定 Go。这个
指示是决定性输入，但仍值得记录它带来了什么、代价是什么——因为架构的其余部分都倚靠这些
后果。

有三股力量在相互拉扯。系统必须**可演示**——它得在现场、在一台没人事先准备过的机器上可靠
启动。它必须**确定**——自主开发循环无法验证它无法复现的东西。它还必须**作为设计可读**：
编排正是这项工作的实质，因此流程应当以代码的形态可见，而不是由框架配置拼装出来。

依赖树通常是这三方面失败的共同来源。每个模块都意味着一次构建期网络调用、一次版本解析，
以及一段测试并不拥有的行为。

## 决策

我们将仅使用 Go 标准库实现整个系统。`go.mod` 不携带任何 `require` 指令，并由测试断言
这一点。外部系统通过手写端口访问，其默认适配器在进程内。

## 后果

### 正面

- 制品是单个静态二进制；容器镜像等于一个基础层加一个文件。构建无需模块代理。
- 并行证据采集所需的并发是语言原语，而确定性要求（REQ-0061）可以通过对贡献排序来强制，
  而不是去协调某个框架的调度器。
- 状态机、轮次预算、覆盖守卫与审批门都是同一个包内的显式代码。评审者可以完整读完控制流。
- 供应链攻击面为零。`go vet` 与竞态检测器覆盖整个系统。

### 负面

- 没有 agent 框架、没有 HTTP 路由库、没有模板引擎、没有测试断言库。大约数百行基础设施
  需要手写并测试——路由、SSE、一层小模板、夹具加载。
- 没有现成的模型客户端。模型适配器（ADR-002）接入时必须直接对着服务商的 HTTP API 编写。
- 用 `encoding/json` 处理 JSON 比能生成模式的库更啰嗦，校验也要显式书写。

### 中性

- 配置采用 JSON 而非 YAML，因为标准库只解析前者。对于这么小的配置面，这只是外观差异。

## 已考虑的备选方案

| 备选方案 | 它的吸引力 | 为何落选 |
|---|---|---|
| Python + FastAPI + agent 图框架 | 通向可用 agent 循环的最快路径；这个问题通常就是在该生态里解决的 | 被项目负责人否决。独立来看：要装一个运行时加一整套依赖，而编排——工作的真正主题——会变成框架配置而非可读代码 |
| Go 加少量精选库（路由、YAML、断言） | 为一些确实平庸的代码带来一点便利 | 每一个都是构建期网络依赖与需要维护的版本，换来的却是本就小而稳定的代码。CON-008 要求为此给出理由，而理由并不充分 |
| Rust | 更强的保证，部署形态相当 | 对一个 I/O 密集的编排服务没有优势，而且在有期限的前提下抵达可用 MVP 更慢 |

## 重新评估触发条件

出现一个标准库确实无法满足的需求——真正的数据库适配器、终结 TLS 的网关，或者协议复杂到
不适合手写的模型客户端。届时针对该依赖单独修订本 ADR，而不是整体废止。
