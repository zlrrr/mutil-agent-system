# ADR-002 — 以确定性规则推理器为默认，模型适配器置于端口之后

**状态。** accepted

**日期。** 2026-08-05

## 背景

这是一个多 Agent 系统，而 Agent 最显然的实现方式就是调用语言模型。但有两条需求使它不适合
作为**默认**。

REQ-0090 要求相同输入离线产生相同输出。采样模型给不了这一点，把温度钉成零也给不了——
服务商会变，而对生成文本做断言的测试，本质上是在对厂商的下一个版本做断言。

CON-010 要求开发在没有人在环的情况下推进。自主循环靠跑测试来验证自己的工作；如果测试无法
区分"回归"与"重新采样"，这个循环就没有基准真值，也就无法推进。

还有一条演示层面的考虑，虽然分量较轻但真实存在：一个核心机制依赖可达端点的系统，恰恰会在
它本该给人留下印象的场合翻车。

一个诱人的做法是把确定性路径做成桩件——为演示场景硬编码一个答案，然后在 README 里写"真实
系统会调用模型"。那是不诚实的工作：离线模式将无法证明关于流程的任何事情。

## 决策

我们将定义一个覆盖假设形成与质疑的 `Reasoner` 端口。默认适配器是基于声明式故障签名目录的
真实规则推断引擎：每条签名声明它所需的证据模式、它产出的机理叙述，以及能够反驳它的区分性
证据。模型适配器实现同一端口，由配置选择。

模型输出在被使用时被视为不可信的结构化数据，与规则输出一样要通过完全相同的贡献校验、证据
绑定与策略检查。

## 后果

### 正面

- 完整流程——采集、假设、质疑、索证、处置、审批、验证、报告——由测试套件离线检验，因此
  推理器之上的每条需求都无需服务商即可验证。
- 对抗机制变得**可逐规则测试**：每条质疑规则都能在构造的夹具上被触发，而这在面对生成文本
  时无法可靠断言。
- 签名是数据（ADR-006），因此扩展覆盖是一次可以按 diff 评审的数据变更。
- 替换为模型不改变任何契约、任何状态迁移、任何存储模式。

### 负面

- 规则引擎的泛化能力止步于它的目录。签名缺失的故障不会被提出为假设，而模型也许能猜得
  有用。
- 目录是一个维护面，且可能对演示场景过拟合——这是已认领的风险（R2），通过标注样本量与
  日志误导样例来缓解。
- 两个适配器必须保持行为兼容，这需要一套共享契约测试。

### 中性

- 该系统最准确的描述是"推理策略可插拔的多 Agent 系统"，而不是"LLM 应用"。手册会直说这
  一点，而不是暗示一种默认实现并不具备的模型参与度。

## 已考虑的备选方案

| 备选方案 | 它的吸引力 | 为何落选 |
|---|---|---|
| 只用模型推理这一种实现 | 符合人们对多 Agent 系统的预期；泛化更好 | 放弃 REQ-0090，并让自主循环失去基准真值。测试将不得不对散文做断言 |
| 模型温度置零并缓存响应 | 实践上的确定性；保留模型推理的核心地位 | 只在缓存未失效、服务商未变更之前可复现。缓存不是规格 |
| 为演示返回固定答案的确定性桩件 | 构建极简单；演示看起来一模一样 | 无法证明关于流程的任何事情。推理器之上的每条需求都将失去测试 |
| 模型 + 基于规则的后置校验 | 兼得泛化与安全 | 校验能抓住格式错误的输出，抓不住采样方差。确定性要求针对的是**排序**，而校验并不能稳定排序 |

## 重新评估触发条件

评估显示规则目录在签名集合之外的样例上排序失败，**并且**出现了输出可被充分固定、足以让
测试套件仍然有意义的服务商。届时模型适配器成为部署默认，规则适配器仍作为测试默认。
