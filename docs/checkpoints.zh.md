## 已知问题

**评分会为一个解释从未声明的证据扣分（D13）。** 签名的分数是六个加权项之和，但其中三项
——指标、日志、变更吻合度——只对"要求该类证据"的签名适用。`sig-traffic-surge` 只要求一条
指标。在该指标完全匹配的情况下它得到 0.47，理论上限是 0.55，因此永远越不过 0.75 的接受
阈值。它可以被**排到第一**，在 C4 中确实如此；但它永远无法被**执行**。

显而易见的修法是"只在适用的项上做归一化"。我把它实现并实测了，结论是：这个修法是错的。

| 样例 | 修改前的领先者 | 修改后的领先者 | 影响 |
|---|---|---|---|
| C1 第 1 轮 | `sig-traffic-surge` 0.49 | `sig-traffic-surge` 0.89 | 越过阈值、差值 0.45——质疑者根本不会触发 |
| C1 最终 | `sig-db-pool-exhaustion` 0.94 | 0.94 | 结论仍正确，但已不再经由对抗轮得出 |

归一化会让"只有一条要求"的解释轻易接近确定：匹配它唯一的要求，按构造就等于匹配了它所要求
的全部。于是参考场景会在第 1 轮以高置信度接受错误答案——而这恰恰摧毁了整个项目赖以成立的
那个论证。四个测试抓到了它——分差过小规则、两个模式对比中的轮数断言、以及升级测试——因此
我们回滚了改动，而不是去迁就它修改测试。

真正的缺陷在目录建模而非算术："流量上涨了"并不等于"流量**导致**了故障"。这个解释本应要求
那份"负载超过历史已服务水平"的对比证据——也正是 C1 用来否定它、C4 用来确认它的那份证据。
这是对 `signatures.json` 的建模改动，自带级联，因此选择推迟，而不是与一个新故障样例
仓促地混在一起做。

**当下的后果。** C4 把正确原因排在第一，并以反证否定了两个对手——这正是 TC-0104 断言的
内容，也正是过拟合测试所需要的。它停在接受阈值之下，而不会提出它所声明的处置。该样例仍然
声明 `expected_remediation`，因为那确实是正确的动作；只是系统目前到不了那一步。

## 升级记录

有一条，已经提出并随后解决。这里保留而不是删除，因为 CON-010 要的是这个循环做了什么，
而不只是它最后停在哪里。

**提出：推送到远端曾被组织策略阻断。** `git push` 返回 `403`，API 直接给出了原因——
*GitHub access is not enabled for this session. An org admin must connect the Claude
GitHub App for this organization.* 全程读取都是可用的（`git ls-remote` 与 API 的读取
端点都成功），代理也未报告任何中继失败，因此这是一条授权边界，而不是网络或凭据故障。
三条写入路径均已尝试，且都被拒绝：

| 路径 | 阻断期间的结果 |
|---|---|
| 经 HTTPS 的 `git push` | `403` |
| 用会话令牌调用 `POST /repos/.../git/refs` | `403 GitHub access is not enabled for this session` |
| GitHub App 集成 | `403 Resource not accessible by integration` |

既然拒绝发生在授权层，那么重试与绕行都是错的做法：循环就此停下，把阻塞写进本日志，
使它随制品一同留存、而不是只活在一次对话里，并指明唯一能解除它的那个动作。

**解决：写权限已授予，分支已推送。** `git push -u origin
claude/project-spec-architecture-78dmtj` 现已成功。本地与远端的领先/落后计数均为
`0 0`，远端因此完整承载了每一次提交、顺序与提交信息俱在——没有压缩历史，也没有逐文件
重传。

**解决：release 已切出，走的正是这次阻塞逼我们建出来的那条路。** 分支推送可以成功，但
推送**标签**返回 `403`，说明写权限是按分支授予的。其余每条路径也都被拒绝：

| 路径 | 结果 |
|---|---|
| `git push origin v0.1.0` | `403`（表面上表现为 sideband 断连；`--verbose` 才显示真实状态码） |
| 用会话令牌调用 `POST /repos/.../git/tags` | `403 Write access to this GitHub API path is not permitted through this proxy` |
| GitHub App 集成（`workflow dispatch`） | `403 Resource not accessible by integration` |

由于被卡住的恰恰是**标签**这一环，工作流因此新增了一个手动入口，而不是继续依赖那唯一
缺失的权限。随后维护者合并了分支并运行了该入口：工作流运行 `31041990777` 十八个步骤
全部完成，发布了 `ghcr.io/zlrrr/mutil-agent-system:0.1.0` 与 release `v0.1.0`，并附上
二进制、可加载镜像 tar 包与 `SHA256SUMS`。

这条经验值得随阻塞一起留下而不是一并删掉：在约束下造出来的那条应急通道，如今成了从浏览器
切 release 的常规方式。

连同上面那条推送阻塞，这是本里程碑中自主循环仅有的两次需要它并不具备的授权
（CON-010）。其余决策都不需要：每一处歧义都能由章程、需求或宪章解决。章程记录的三个
开放问题（Q1–Q3）没有阻塞任何 M1 工作，各自都按章程声明的默认假设推进。
