## 检查点抓到的缺陷

以下是门禁抓到的问题，以及由此产生的改动。之所以记录，是因为一个从不失败的检查点不算
检查点。

| # | 发现方 | 问题 | 处理 |
|---|---|---|---|
| D1 | 批次 0 的 `sddctl trace` | 治理工具自身的源码先于它所实现的设计条目存在 | 先编写覆盖 DLD-0101..0109 的 `specs/000-sdd-framework`，再继续 |
| D2 | 首次端到端运行 | 变更采集器的默认趟使用了分析窗口（起点比告警早七分钟），因此它立刻就找到了配置变更，质疑者的索证也就失去了意义 | 默认趟改为从告警时刻起查询；只有当索证要求时才施加扩展回看（DLD-1040） |
| D3 | 首次端到端运行 | `change_correlation` 拿变更与 case 中**最早**的任意异常比较。流量序列动得更早，于是真正的原因得分为零 | 改为与该假设**自身**支持指标的起点比较（`HypothesisOnset`，DLD-1032） |
| D4 | 首次端到端运行 | 所有裁决都是空：`CombineVerdicts` 把未设置的裁决视为最严重，于是它压过了所有真实判定 | 跳过未设置的裁决；"尚未判定"不再压过一个决定 |
| D5 | 首次端到端运行 | 第 1 轮的 `revise` 裁决延续到第 2 轮，因此回应了挑战的证据永远无法解除它 | 裁决不再跨轮携带；质疑者针对本轮证据重新审查每个假设（DLD-1033） |
| D6 | TC-0062 | 分诊步骤发出的 `agent_completed` 没有耗时，事件日志中的工作记录因此不完整 | 分诊现在会对自身计时，并给出它计划扇出的采集器清单 |
| D7 | `sddctl gate --stage architect` | 有 13 条需求没有任何架构条目派生自它——这是真实的覆盖缺口，不是工具产物 | 扩展 ARC-003、ARC-004、ARC-006、ARC-010、ARC-011 与 ARC-014 以认领它们 |
| D8 | TC-0091 | REQ-0091（无第三方依赖）没有已执行的测试，因为验证它的那个测试只链接到框架自身的需求 | TC-9013 现在同时派生自 REQ-9013 与 REQ-0091 |
| D9 | TC-0092 | 发布流水线的顺序断言匹配到了该文件自己的头部注释——注释里提到了 `docker push`——于是它把一条注释当成了发布步骤，判定一个正确的工作流失败 | 断言先剥离整行注释：描述流水线的散文无法发布任何东西。已通过把发布步骤移到门禁之前（测试失败）再还原（测试通过）确认该断言是活的 |
| D10 | `TestPlaneDependencies` | 三个新增的适配器包不在依赖表中，因此没有任何东西约束它们可以 import 什么 | 已为它们分配层级：在线适配器与夹具适配器并列，是它的替代品；profile 选择高于所有适配器、低于所有端口消费者 |
| D11 | 手动 CLI 检查 | `arena serve --signal-profile prod` 干净地启动了。未知 profile 只有在创建第一个 case 时才被拒绝，于是一套拼错的部署看起来很健康，随后在已经有人依赖它的时候一个 case 接一个 case 地失败 | 新增 `profile.Config.Validate()` 并在启动时调用；入口以 2 退出并指明出错的 flag |
| D12 | 复查 TC-0102 | 日志测试里那条"对抗性载荷"含有类似帧头的字节，却没有换行符，因此一个朴素的逐行解析器同样能通过——该测试并未断言分帧解析器所独有的任何性质 | 载荷改为一条真正的多行记录，其续行以帧头字节开头，断言现在要求两半必须落在同一条记录里 |
| D13 | 构建 C4 时 | `sig-traffic-surge` 在它唯一声明的项上拿到 1.00，总分却被压在 0.55 附近，因为它从未要求的那些项被当作零计入。于是任何只要求一类证据的解释，无论支撑多强，在 0.75 阈值下都不可能被接受 | **未修复——见下方已知问题。** 那个显而易见的修法会让情况更糟，而交付一个错误的修复比交付这个缺陷更糟 |
| D14 | `sddctl lint` | 新增的详细设计条目复用了 `DLD-1034`，而该标识符已被质疑规则条目占用。工具拒绝了这棵树，而不是让两份设计对应同一个标识符 | 改号为 `DLD-1035`；源码锚点随之更新 |
| D15 | `sddctl gate --stage architect` | REQ-0100 没有任何架构条目派生自它——与 D7 同类的缺口，也由同一道门禁抓到 | 扩展持有推理器端口的 ARC-005 以认领它 |
| D16 | 构建 C5 时 | `source_vs_victim` 从未在任何端到端运行中触发过：此前每个样例的告警服务同时也是源头。它有单元测试，此外一直休眠——一条没人看着它真正工作过的规则 | C5 的告警落在受害者身上。运行它暴露了下面的 D17 与 D18 |
| D17 | C5 首次运行 | 该规则只挑战、不索证，于是 case 带着一个 `revise` 裁决在第 1 轮就收尾，从未看向上游。一个没有任何证据能够回应的挑战，是否决而不是质疑 | 规则现在索取目录中每条尚未被回答的要求描述符——正是这些让上游解释得以形成 |
| D18 | C5 第二次运行 | 该规则连"正确归咎于上游"的那个解释一并挑战，用的还是支撑它的那份拓扑证据。第一次修复尝试从签名的处置服务字段读取意图——但本目录中每条签名的处置都指向 `order-api`，于是每个解释都显得"已看向上游"，规则彻底不再触发 | 改为由证据判定：索证响应把它所涉及的服务记录在 `subject` 事实中，而一个建立在上游证据之上的假设并不是在描述受害者 |
| D19 | C5 第二次运行 | 变更与日志的索证响应按**告警**服务过滤，因此受害者的告警永远取不到其上游的历史——"告警服务即调查主体"这个假设不只写在规则里，也写进了夹具 | 索证响应可以指定 `Service`，默认为告警服务 |

### 为 C1 重设计做准备时发现的缺陷

| # | 问题 | 处理 |
|---|---|---|
| D24 | 异常检测器只认得"增长"。一条**塌陷**的指标——可用性量表跌到零、吞吐量走平、队列被抽干——对它完全不可见，而这些恰恰属于一次故障所能产生的最具诊断价值的信号 | 塌陷按"上升的镜像"检测，并沿用同样的持续性要求，因此单个下探采样仍是噪声；`Summary()` 会说该序列**下跌**，而不会把它错报成上升 |
| D25 | `sig-db-outage` 要求它的可用性指标发生"下跌"，却把这一点表达为 `saturated`——后者由"已声明的容量"算出，可任何可用性量表都没有容量。**该要求不可满足**：这条签名永远无法被采集器产出的任何证据完整匹配；而此前没人注意到，是因为没有任何样例演练过数据库宕机 | 模式新增了通用的 `Facts` 条件——`saturated` 本就该是这个形态——签名改为要求 `collapsed`。六个样例全部不变，因为没有任何一个存在塌陷的量表；这条签名只是从"不可能"变成了"诚实" |

### C6 暴露的缺陷

| # | 问题 | 处理 |
|---|---|---|
| D20 | `temporal_order` 是最后一条从未端到端触发过的质疑规则。C6 让它触发了，并立刻暴露出该检查太窄：它是拿被归咎的变更与 `HypothesisOnset` 比较，而后者衡量的是解释与它**自身**指标的关系。一个先被调小、随后饱和的连接池在内部自洽，却对一场早四分钟开始的故障什么也没解释；于是一旦被索取的连接池指标到位，这条反对意见就自行消失了 | 规则现在还会拒绝那些"自身证据晚于告警超过 `coMovementWindow`"的解释：症状晚于故障本身，就只能是导致故障者的下游 |
| D21 | 被拒绝的解释依然排在第一并被当作答案报告出来——而同一页报告里就记着它被拒绝 | `Leading()` 返回质疑者未曾拒绝的、分数最高的假设；排序仍把被拒绝者排在第一，旁边并列其裁决。"它吻合得最好，以及我们为何拒绝它"对读者的价值高于把它藏起来 |
| D22 | 处置角色作用于排名最高的假设，于是它提议去改那个刚被质疑者排除掉的配置项 | 处置角色改用 `Snapshot.Leading()`；评估的 top-1 指标同样改为报告被接受的解释，而不是系统明确拒绝得出的那个结论 |
| D23 | 扩展窗口内有两次变更时，变更索证只返回最后一次——于是一个落在起点**之后**的发布，遮蔽了它之前那次变更，而唯一可能导致任何后果的那次变更从未成为证据 | 索证问的是"起点之前的变更"，因此响应现在就以一次这样的变更作答：告警之前最近的那一次。起点之后的变更仍由默认趟采集到，那才是它该在的位置 |

### C1 重设计暴露的缺陷

| # | 问题 | 处理 |
|---|---|---|
| D26 | `alternative_explanation` 索要了第 1 轮**已经采集到**的数据库可用性指标。`demandAlreadyAnswered` 只认得"作为索证回答而到达"的证据，因此案件默认查询采到的证据对它不可见。C1 为此白花了第三轮采集，去重取第 1 轮已经读过的序列 | 当对手自身已匹配的要求就提供了某条区分性证据时，该条同样被跳过。质疑者手上有没有那份区分性证据，不应取决于它是怎么拿到的。C1 回到两轮 |
| D27 | 这条新的区分性证据在 C4 里也会被索要，而 C4 没有任何来源能回答它——一条未被回答的索证，意味着同一条 `revise` 质疑会在每一轮被重新提到领先者头上。C4 于是什么也没接受：烧光预算、升级到人工复核、并报告了错误的原因。**一条带着"没人能满足的索证"的规则，就是多绕了几步的否决**——与 D17 是同一个形状，只是从另一扇门进来 | 携带未消解反证的对手会被跳过：证据已经反对过它，它就不再是这条规则要抓的"未经检验的替代解释"。C4 回到接受 `sig-traffic-surge` |
| D28 | 修 D27 时发现：一条某轮采集没能回答的索证，会被当作"再跑一轮"的理由，每一轮都是，直到预算耗尽。C5 从写出来那天起就带着四条这样的索证。上一次变更把它记录为未修复，随后的这次变更修掉了它 | 索证记录它首次被提出的轮次；`afterCritique` 只为本轮提出的索证返回采集阶段，且每条规则都不再重复发出上一轮已经尝试过的描述符。未满足的索证仍会被报告，并区分"预算耗尽"与"没有来源能回答它"。C4 回到两轮，C5 不再每轮重复三条索证，平均轮数 2.50 → 2.33，六个样例依然全部正确 |
| D29 | 为 D28 写 TC-0111 时发现：这个修复的第一版只改到了四条会发出索证的规则中的三条。`source_vs_victim` 仍在每轮重复发出它那三条上游描述符，而只测 C4 的测试照样通过——因为 C4 的重复走的是 D27 修复已经堵住的那条规则 | 测试改为同时断言 C4 **与** C5，因为提出它们索证的规则不同，而每条规则各自决定要不要重问。现在把修复回退掉，会在 C5 上失败——这正是只测 C4 的版本做不到的事 |

### C2、C3 重设计暴露的缺陷

| # | 问题 | 处理 |

### M6 —— 让模型推理器可被度量

| # | 问题 | 处理 |
|---|---|---|
| D34 | **确定性推理器是在没有升级请示的情况下被采纳的。** `project.md` 指定了 Python、LangGraph，以及"每个 Agent 一个 system prompt"；ADR-002 用 Go 规则引擎替换了它，理由之一是 REQ-0090（逐字节相同的输出）——那是本项目**自己写给自己**的需求，目标文档里并没有这一条。CON-010 要求**范围变更**必须升级请示而不是自行决定；替换掉参考架构的核心技术就是范围变更。这个决定被诚实地记进了 ADR，却从未交给定下目标的那个人 | 在发现它的这次会话里补做了升级请示。规则引擎继续作为**测试**基底，因为 CON-010 的自主循环确实需要一个采样模型给不了的 ground truth；而它是否继续作为**产品**默认值，现在是一个交给目标所有者的开放决定（M7），而不是本项目在 ADR 里自行了结的事 |
| D35 | ADR-002 把"两个适配器必须保持行为兼容，这需要一套共享契约测试"列为后果，而那套测试从未被写出来。整整五个里程碑里，两个适配器只被同一个 Go 接口——一个**形状**——约束着。更糟的是，选择方式只能从 `arena serve` 抵达：那恰恰是唯一不产出对照的命令。于是"换成模型不改变任何契约"这个声称，从任何会产出结果的入口都**不可证伪** | REQ-0104 把选择方式同时放到 `serve`、`demo`、`evalctl` 上；REQ-0105 用同一套行为测试约束两个适配器；REQ-0106 把适配器名称带到每个 case 与每一行评测结果上。`evalctl run --reasoner rule,model` 现在一次调用就产出对照 |

## 已知问题

**评分会为一个解释从未声明的证据扣分（D13）。** 签名的分数是六个加权项之和，但其中三项
——指标、日志、变更吻合度——只对"要求该类证据"的签名适用。`sig-traffic-surge` 只要求一条
指标。在该指标完全匹配的情况下它得到 0.47，理论上限是 0.55，因此永远越不过 0.75 的接受
阈值。它可以被**排到第一**，在 C4 中确实如此；但它永远无法被**执行**。

显而易见的修法是"只在适用的项上做归一化"。我把它实现并实测了，结论是：这个修法是错的。

| 样例 | 修改前的领先者 | 修改后的领先者 | 影响 |
|---|---|---|---|
| C1 第 1 轮 | `sig-traffic-surge` 0.49 | `sig-traffic-surge` 0.89 | 越过阈值、差值 0.45——质疑者根本不会触发 |
| C1 最终 | `sig-db-pool-exhaustion` 0.94 | 0.94 | 结论仍正确，但已不再经由对抗轮得出 |

归一化会让"只有一条要求"的解释轻易接近确定：匹配它唯一的要求，按构造就等于匹配了它所要求
的全部。于是参考场景会在第 1 轮以高置信度接受错误答案——而这恰恰摧毁了整个项目赖以成立的
那个论证。四个测试抓到了它——分差过小规则、两个模式对比中的轮数断言、以及升级测试——因此
我们回滚了改动，而不是去迁就它修改测试。

看上去真正的缺陷在目录建模而非算术："流量上涨了"并不等于"流量**导致**了故障"。这个解释
本应要求那份"负载超过历史已服务水平"的对比证据——也正是 C1 用来否定它、C4 用来确认它的
那份证据。

**这一版同样被实现并实测了，结论也是错的——但错得更有意思。** `sig-traffic-surge` 新增了
两条要求：负载必须超过此前已服务的任何水平（对对比证据施加事实条件），且服务必须报告在
丢弃负载。这把它的上限从 0.55 抬到 0.80，接受因此变得**可达**而不再是构造上不可能；C4 也
从 0.47 升到 0.72、裁决为 `accept`。C2、C3、C5、C6 均不受影响。

随后有两个测试失败了，而它们说的话比这次改动本身更重要：

> the single-agent mode reached the correct root cause; the comparison would demonstrate nothing
> multi_no_critic reached the correct root cause; the comparison would be vacuous

一条被恰当刻画的签名，已不足以在 C1 第 1 轮胜出——于是质疑者再没有什么可纠正的，基线也
就无需帮助地解出了参考场景。**C1 的头号结论，依赖于 `sig-traffic-surge` 被刻画得不充分。**
这个论证靠的是一处建模弱点，而不是"单趟推理"的某种固有性质；修好这个弱点，论证也就随之
消解。

这一点值得被准确地记下来，而且它不是一个评分补丁能解决的。真正该做的，是重新设计 C1，
让它第 1 轮的错误建立在"即便目录被恰当刻画也依然成立"的理由之上——一个细致的推理者仍会
先想到、并且仍不得不放弃的合理解释。

**这个重设计现在已经完成（REQ-0103、TC-0110），因此第三次尝试做了——而它因为第三个理由
再次失败。** C1 第 1 轮的错误是一次真实的两分钟数据库宕机，它不再依赖 `sig-traffic-surge`
被刻画得薄弱：即便收紧了该签名，C1 的基线依然回答 `sig-db-outage`，依然是错的。拦路石
换了一块。

`sig-traffic-surge` 增加了与上次相同的两条要求，上限从 0.55 抬到 0.80。六个样例上的实测
结果：

| 样例 | 模式 | 之前 | 之后 |
|---|---|---|---|
| C1 | multi_with_critic | 正确，2 轮 | 正确，3 轮 |
| C2、C3 | multi_with_critic | 正确，2 轮 | 正确，3 轮 |
| C4 | multi_with_critic | 正确，3 轮 | **错误**——`sig-db-pool-exhaustion` |
| C2、C3 | single、multi_no_critic | 错误 | **正确**——基线自己就解出来了 |

每个样例都跑到了三轮的天花板，而 C4——那道过拟合防线——垮了。原因是 D28：新增的两条要求
带来了大多数样例无法回答的索证（`load shedding log sample`，以及把历史对比从"区分性证据"
提升为"要求"），而一条无人能答的索证会每轮重试，直到预算耗尽。C2、C3 变得单趟可解，则是
同一条 D13 教训从另一侧传来：它们的头号结论同样建立在"`sig-traffic-surge` 是那个廉价的
第一答案"之上。

这次改动在六个样例上被实测，并第三次回滚。

**随后两个前置条件都完成了——D28 已修复，C2 与 C3 已重设计——于是做了第四次尝试。** 它是最
接近成功的一次，但依然失败。

在头号指标上它是成立的：六个样例在质疑者下全部正确，而基线从 1/6 掉到 0/6——因为 C4 的基线
此前答对，靠的本来就是错误的理由。可在这层之下，有三件事坏掉了。新增的两条要求让每一轮多出
两条覆盖缺口索证，而在"每轮四条"的上限下，具有区分力的证据被挤了出去：C1、C2、C3 不再**驳倒**
它们的首轮领先者，而只是在分数上压过它们——这恰恰是 REQ-0103 存在的意义。把上限提到 6，反证
回来了，坏掉的换成了别的：C1 多出一条永远无法满足的索证（一份它根本不存在的负载丢弃日志），
三个编码了目录特定排序的单元测试失败，而且 **C4 依然无法对它自己已接受的解释采取行动。**

最后这一点是决定性的。C4 无法行动，正是 D13 所描述的那个后果；一个要付出配置改动、三个测试
重写、以及参考场景里一条永久未满足索证的修复，若**仍然**交付不了它本来要交付的东西，那它就
不是修复。第四次回滚。

**当下的后果。** C4 把正确原因排在第一，并以反证否定了两个对手——这正是 TC-0104 断言的
内容，也正是过拟合测试所需要的。它停在接受阈值之下，而不会提出它所声明的处置。该样例仍然
声明 `expected_remediation`，因为那确实是正确的动作；只是系统目前到不了那一步。

**已尝试的方案，按先后顺序。** 对权重做归一化（错：会让只有一条要求的解释轻易接近确定，
于是 C1 在第 1 轮就接受错误答案）。收紧签名（错：会移除 C1 赖以存在的那个第 1 轮错误）。
在 C1 重设计消除了上一条反对之后再次收紧签名（错：新增的要求会产生没有样例能回答的索证，
而 D28 把它们变成被耗尽的轮次预算——C4 垮掉，C2、C3 变得无需质疑者即可解出）。在两个前置
条件都满足后第三次收紧签名（错：新增的索证在"每轮四条"下把区分性证据挤了出去；而提高上限
换来的是一条永久未满足的索证、三个被重写的测试，以及一个依然无法行动的 C4）。四者都被
实现、在全部六个样例上实测，并依据证据回滚，而不是靠争论定夺。

**四次尝试确立了什么。** 缺陷在算术里，不在目录里：一条签名会为它从未声明过的证据类别付出
代价。迄今每一次尝试都是绕过这一点——让签名去声明更多——而每一次都在不同的地方失败，这本身
就是结论。下一次尝试应当改变"评分如何对待一条签名并不要求的项"，并且必须对着 REQ-0103 所
陈述的性质来度量，而不是对着 top-1 准确率：因为在一次已经悄悄拆掉了全部反证的尝试里，top-1
始终停在 100%。
